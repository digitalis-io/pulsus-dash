# Pulsus Dash → PulsusDB: requirements

> For: PulsusDB engineering. From: Pulsus Dash design (UI-first). Date: 2026-11-17.
> Checked against `digitalis-io/pulsusdb` `origin/main` `docs/api.md` and the issue tracker on that date.
> **Revised 2026-11-18** after the Dash technical designs ([T03–T20](../README.md#technical)) were checked against
> `origin/main` source: R3/R5/R7 fallbacks corrected, R4 and R10 amended, R16 added, and the known
> limits that Dash designs around are listed in §0.1.
> **Revision 3 (2026-11-18), after product decisions:**
> - Dash no longer writes derived series into PulsusDB ([ADR-0012](../adr/0012-derived-state-in-postgres.md)),
>   so the R4 fallback no longer uses ingest.
> - The R5 edge-cap raise is now a **planning assumption** (A1).
> - R17 is downgraded to P3, because Dash is AGPL-3.0 too.
>
> **Revision 4 (2026-11-19):** the PulsusDB owner confirmed the native routes Dash uses, including the
> service graph at `/api/traces/v1/service_graph?start=<t>&end=<t>` on the native traces API. The
> route exists; the R5 edge-cap raise remains assumption A1.
>
> **Revision 5 (2026-11-19):** the Dash backend is now written in Go and the web client in
> TypeScript, with a Rust/WASM chart engine added later
> ([ADR-0015](../adr/0015-go-bff.md), [ADR-0014](../adr/0014-typescript-react-web-client.md)). PulsusDB's
> Rust parser crates are now used only in the browser, compiled to WASM for editor diagnostics (R17);
> the BFF parses no query language in v1 and validates queries by sending them to PulsusDB. How the
> later data-scope rewrite (R12 fallback, M-UI6) parses queries is an open question for T10 (draft).
> No ask changes priority.
>
> **Revision 6 (2026-11-25):** Dash converts PulsusDB's JSON to Arrow in the BFF as its committed
> path (owner direction, [ADR-0005](../adr/0005-arrow-wire-format.md) as amended), so R1 drops from
> P0 to **P2**: optional, nothing in Dash waits for it.
>
> **None of these block Pulsus Dash.** Every requirement has an interim fallback that the Dash
> backend-for-frontend (BFF) implements first; PulsusDB support replaces the fallback when it lands,
> usually with a large performance or fidelity gain. Priorities follow the Dash UI milestones
> ([12](../product/12-roadmap.md#2-ui-milestones)).

### 0.1 Known limits Dash designs around (no action unless noted)

| Limit (verified on `origin/main`) | Dash handling |
|---|---|
| `service_graph`: no `q`/filter, no `step`, capped at **1 000 edges** (`SERVICE_GRAPH_MAX_EDGES`) | Atlas at 10k services / 50k edges needs partitioning; see **R5** (amended) |
| Metrics: **resource attributes are not promoted onto series** (`service.*` → `job`/`instance`, the rest → `target_info`) | Entity derivation joins via `target_info` ([T12](T12-entity-catalogue.md)); data scopes on resource attributes can't be enforced on metrics by rewriting, so they fail closed (T10 (draft)); see **R16** |
| TraceQL structural operators work in search but **not in metrics queries** | Error-origination fallback is sampled search only; see **R7** |
| TraceQL metrics `by()` capped at 1 000 series; trace tag values 1 000 per request | Planner partitions by service set ([T07](T07-scene-query-planner.md)) |
| `query_range` ≤ 11 000 intervals (TraceQL metrics 10 000); LogQL metric results > 500 series are an error | Planner splits ranges and groups ([T07](T07-scene-query-planner.md)) |
| Profiles: 7-day look-back floor, 24 h maximum window | No "months" scrub for profiles; −7d profile baselines are limited ([T04](T04-wire-format-and-data-plane.md)) |
| Metric rollup levels 60 / 720 / 7200 / 86400 s, chosen by time range (not step) | Dash pyramids use the same lattice; the planner predicts the level ([T07](T07-scene-query-planner.md), T13 (draft)) |
| `X-Pulsus-Explain` bypasses the read cache | Dash predicts exactness and samples explain at ~1 % ([T06](T06-bff-architecture.md)); see **R10** |
| Ruler is off by default (`PULSUS_RULER_ENABLED=false`) and runs in mode `all` only | R4 fallback must handle a disabled ruler; see **R4** |
| TraceQL metrics returns its native trace-metrics body, not a PromQL matrix | BFF converter handles both ([T04](T04-wire-format-and-data-plane.md)) |
| API auth is Basic only (default admin `admin`/`admin`) | Dash uses per-tenant service credentials; see **R12** |

## 1. Requirements

Priority: **P0** = needed for M-UI0–2 performance targets · **P1** = M-UI3–4 (Atlas, RCA) · **P2** = later.

### R1 (P2, was P0) — Columnar binary response format for bulk numeric results

**Why:** today's Prometheus-style JSON sends sample values as strings. Decoding 10⁷ of those in WASM
blows the frame and memory budgets ([09](../product/09-performance-contract.md)). *(2026-11-25: Dash
never decodes that JSON in the browser; the BFF converts it to Arrow, so R1 would save BFF CPU and
latency only. Optional.)*

**Scope:** `query_range` (PromQL, LogQL metric queries, TraceQL metrics), `volume`, `select_series`
(profiles), and R2's scatter endpoint.

**Required properties (encoding left to PulsusDB — Arrow IPC or deliberately columnar protobuf):**
- Columnar per series: contiguous `int64` timestamps (ms or ns, stated) + contiguous `float64` values; aligned to 8 bytes.
- Series labels sent once per series; repeated label strings dictionary-encoded or in a string table.
- Stale markers / NaN preserved; absent points absent (no fill).
- Streamable in chunks (record batches / length-delimited frames) so the client paints before the body ends.
- Response metadata (truncated, exactness / rollup level, rows read, series count) in a header or trailer block.
- Negotiated by `Accept`; JSON stays the default, so compatibility is unchanged.

**Acceptance:** decoding a 1 000-series × 10 000-point response into typed arrays in Rust/WASM in
**< 50 ms** on an M2 laptop, with ≤ 1 copy of the value data; wire size after zstd ≤ JSON+gzip.
We will share the benchmark harness from M-UI0.

**Dash fallback (the committed path):** the BFF parses JSON and re-encodes to Arrow (`internal/arrowwire`; costs BFF CPU and adds latency, but the browser is fine).

### R2 (P0) — Span scatter points

**Why:** the span scatter (duration × time, every span, up to 10⁷ points) is the hero view of
Lens and Traces ([04 §4.6](../product/04-surfaces.md)). Search (`limit` default 20 traces) and metrics (aggregated) can't produce it.

**Ask:** `GET /api/traces/v1/points?q=<TraceQL filter>&start&end&max_points&fields=` returning
columnar `(start_ns, duration_ns, status, service, trace_id, span_id[, chosen attrs])`, with
deterministic down-sampling past `max_points` (keeping outliers, e.g. stratified by duration
quantile), and the sampling ratio reported.

**Dash fallback:** draw `histogram_over_time` as a heatmap and fetch individual traces only for the brushed region (less precise, but it works).

### R3 (P0) — Entity inventory

**Why:** Pulsus is entity-first ([02 §1.1](../product/02-information-architecture.md)). We need to know which
services, pods and hosts exist and which signals each has.

**Ask:** an endpoint returning distinct combinations of a configurable list of resource attribute
keys (e.g. `deployment.environment, k8s.cluster.name, k8s.namespace.name, service.name,
service.instance.id, host.name`), per signal, with `first_seen`/`last_seen` and a cardinality cap.
It should come from the series/stream/resource indexes, never from raw rows. **Combinations, not
independent value lists:** the co-occurrence of `service.name` with `k8s.pod.name` / `k8s.node.name` /
`host.name` is how Dash derives the service ⇄ pod ⇄ node "runs-on" links ([15 §1](../product/15-estate-navigation.md)).

**Dash fallback:** label-values calls can't give combinations, so the BFF uses the **series** endpoints instead: logs `/series` per cluster, metrics `/series` on `target_info`, scoped trace tag-values, `service_graph`, and profiles series. That is about 205 calls per 60 s cycle at 1M containers, with quiet clusters refreshed every 10 min ([T12](T12-entity-catalogue.md)).

### R4 (P1) — Entity health rollups ("summary pyramids")

**Why:** the Atlas colours 10k entities, and the local analytics engine scrubs months at 60 fps
(01c (research) §3.1). That needs RED per service/operation and USE per host on
PulsusDB's own rollup lattice (1 m / 12 m / 2 h / 1 d, plus a 10 s live level computed by Dash), fetched in bulk for many entities in one request.

**Ask:** either (a) a shipped recording-rule pack using the existing ruler plus rollup levels, documented as
the supported way, or (b) native span-derived RED rollups (rate, errors, duration histogram per service
× operation × minute) like the service-graph minute totals. One bulk read of N entities × window in R1 format.

**Dash fallback:** recording rules registered by the Dash installer through the Rules API (§6), evaluated and stored by
PulsusDB's own ruler; Dash itself writes no series into PulsusDB. The ruler is
off by default and runs in mode `all` only, so when it is unavailable Dash runs the same rule pack itself
("self-ruler") and stores the resulting pyramid tiles in **Dash's Postgres**, not in PulsusDB
([ADR-0012](../adr/0012-derived-state-in-postgres.md)). That costs BFF CPU and Postgres storage, so
(a) or (b) is strongly preferred.

### R5 (P1) — Service graph over time

**Why:** Atlas replay and First Light need edge time series. §4.5 already stores **per-minute edge
totals**, so this looks cheap.

**Ask:**
- an optional `step` (≥ 1 m) on `/api/traces/v1/service_graph` returning per-edge series (calls, failed,
  p50/p95/p99), in R1 format when negotiated;
- a **filter** (service set, or a resource-attribute selector such as environment/cluster) so the graph
  can be partitioned;
- a configurable or lifted **1 000-edge cap**: the Atlas target is 50k edges ([09](../product/09-performance-contract.md)).
  **Dash plans on this landing** (assumption A1 in the [design README](../README.md#3-assumptions)): a cap of at
  least 50 000 edges, configurable per deployment.

**Dash fallback:** N windowed calls (one per step), fine for short windows only. Beyond 1 000 edges, Dash
derives edges from TraceQL metrics grouped by client/server service, partitioned under the `by()` cap
([T07](T07-scene-query-planner.md)).

### R6 (P1) — Compare for logs and metric labels

**Why:** Universal Compare must work on every signal (01c (research) §3.2);
today only TraceQL `compare()` does.

**Ask:** selection vs baseline attribute distribution for (a) log stream labels, structured metadata
and detected fields, given a selector, a selection window/filter and a baseline; (b) metric series labels
given a selector and a selection condition. Return per-key value counts for both sides plus totals, so the
client ranks divergence and also shows **unchanged** keys.

**Dash fallback:** the BFF runs paired `count by (label)` / `detected_fields` queries and diffs them (works, but needs N queries).

### R7 (P1) — Error origination per service

**Why:** "victim vs probable origin" ([01a §2.1](../product/01a-audiences-and-perspectives.md)) needs to tell
errors a service *originated* apart from errors it *propagated* from a child span.

**Ask:** an aggregation (TraceQL metrics extension or a dedicated endpoint) giving, per service (and
operation) per step, count of error spans with no erroring child vs with an erroring child.

**Dash fallback:** structural operators are supported in TraceQL **search** but rejected by **metrics**
queries, so the fallback is a *sampled* structural search per candidate service (rates estimated from the
sample), combined with a heuristic from the service graph's failed counts (T15 (draft)).

### R8 (P1) — Version transitions (change feed)

**Why:** deploys are the #1 incident cause; the Change Feed derives them from telemetry with zero config.

**Ask:** per entity, the time ranges during which each `service.version` (configurable attribute) was
observed: `(entity, version, first_seen, last_seen)` over a window.

**Dash fallback:** label-values over consecutive sub-windows, done by the BFF.

### R9 (P1) — Pattern diff vs baseline

**Why:** "NEW log pattern" is top evidence in RCA and Lens.

**Ask:** `patterns` with a `baseline_start/baseline_end`, returning per-pattern counts for both windows
(so NEW / GONE / ↑↓ need no client diffing).

**Dash fallback:** two `patterns` calls, diffed in the BFF.

### R10 (P0) — Uniform response-completeness metadata

**Why:** the coverage meter on every answer (01c (research) §3.10).

**Ask:** one consistent block on every query response (header or envelope key): `truncated`,
`exactness` (raw / rollup level), `sampled` ratio where applicable, shards/replicas that failed or
were skipped, and rows/bytes read. Most of these exist in pieces; the ask is to make them uniform.
Two small additions:
- report exactness **without** the cache-bypassing `X-Pulsus-Explain` (e.g. a cheap response header);
- expose the configured rollup ranges (`PULSUS_ROLLUP_RANGES`) in `runtimeinfo`, so Dash doesn't
  have to mirror the configuration.

**Dash fallback:** per-endpoint parsing of whatever flags exist.

### R11 (P0) — Cancellation reaches ClickHouse

**Why:** the UI aborts superseded requests aggressively ([09 §4](../product/09-performance-contract.md)). A
dropped HTTP request should stop its ClickHouse statements, or panning floods the cluster.
`/metrics` records `499` for client-closed requests; the ask is to confirm (and test) that the
underlying statements are cancelled too, **including on HTTP/2 stream reset** (please also confirm h2/h2c
support). Related: confirm that PulsusDB continues a W3C `traceparent` from the caller, so Dash and
PulsusDB spans join up in one trace.

**Dash fallback:** the BFF rate-limits and coalesces in-flight queries per viewport.

### R12 (P1) — Server-enforced data scope

**Why:** enterprise RBAC must hold even if the BFF has a bug ([11 §1](../product/11-enterprise.md)).

**Ask:** a trusted request header (from authenticated service credentials only) carrying mandatory
label/attribute matchers that PulsusDB ANDs into every selector of every signal. Tenancy
(`X-Scope-OrgID`) already covers the coarse case; this is the finer one. Needed properties: the same
matcher semantics on every endpoint (including `/tags`, `service_graph`, trace-by-id and metadata), the
applied scope's hash echoed in a response header, and a credential that is **only** valid together with
the scope header.

**Dash fallback:** the BFF rewrites queries before sending them (M-UI6). It parses no query language
in v1 ([ADR-0015](../adr/0015-go-bff.md)); the parser for the rewrite (a Go PromQL parser, a LogQL
parser, or this ask) is an open question for Dash's data-scope design.

### R13 (P2) — Batch query

**Why:** a scene plans many viewport queries over one time range; one round trip with shared
planning and a read-cache lookup beats 50 requests.

**Ask:** `POST /api/v1/batch` with `[{id, kind, query, step}]` + shared `start/end`, streaming results tagged by `id`.

**Dash fallback:** HTTP/2 multiplexing of individual requests.

### R14 (P2) — Pre-execution cost estimate

**Why:** query budgets for humans and for the AI agent ([06 §5](../product/06-ai-copilot.md)).

**Ask:** an `X-Pulsus-Explain: estimate` dry-run returning estimated rows/bytes and the chosen rollup without executing.

**Dash fallback:** heuristics from series counts.

### R15 (P2) — Alerting-rule evaluation

Dash evaluates alerts itself at first ([07 §1](../product/07-alerting.md)). When the PulsusDB ruler evaluates
alerting rules (post-1.0), we'd like Alertmanager-compatible notifications plus a state-history query so
Dash can move evaluation into PulsusDB.

### R16 (P1) — Resource attributes usable on metric series

**Why:** metric series carry `job`/`instance` only, with other resource attributes on `target_info`.
Data scopes such as `deployment.environment=prod` or `k8s.namespace.name=payments` therefore cannot be
enforced on metrics by query rewriting, and entity derivation needs a join
(T10 (draft), [T12](T12-entity-catalogue.md)).

**Ask:** either (a) a configurable list of resource attributes promoted onto metric series at ingest,
or (b) server-side matching of selectors against `target_info` attributes (an implicit join), usable
by R12.

**Dash fallback:** metrics are **denied** under a scope that uses non-promoted attributes (fail
closed), and the UI shows the collector-side fix (an OTel processor that copies the attributes onto
datapoints).

### R17 (P3, was P1) — Permissively licensed syntax crates

**Why:** Dash compiles PulsusDB's PromQL/LogQL/TraceQL parsers to WASM for in-browser editor
diagnostics ([T09](T09-query-editors.md)). Since the Dash BFF is written in Go
([ADR-0015](../adr/0015-go-bff.md)), the crates are no longer used on the server.
The crates are AGPL-3.0-only, so linking them makes Dash a combined AGPL work, which constrained the Dash
licensing decision (Q8, since closed by decision D3 in [12](../product/12-roadmap.md#3-decisions-taken)). They compile to `wasm32` today
(`pulsus-logql` ≈ 44 KB, `pulsus-traceql` ≈ 34 KB, `pulsus-promql` ≈ 481 KB gzip).

**Downgraded:** Pulsus Dash is licensed AGPL-3.0, the same as PulsusDB, so linking the crates is
licence-compatible. This becomes relevant again only if a non-AGPL Dash edition is planned.

**Ask:** release syntax-only crates (lexer, parser, AST, printer; no execution) under Apache-2.0/MIT,
e.g. split out `pulsus-promql-syntax`, `pulsus-logql-syntax`, `pulsus-traceql-syntax`. Confirm the
licence of PulsusDB's patches to the vendored `promql-parser`. Nice to have: public lexers, source
spans on AST nodes, and error recovery for editor use.

**Dash fallback:** the parsers sit behind one `QueryLanguage` interface in the Dash client; without
the crates, validation goes through the BFF to PulsusDB, as it does before the WASM build exists.
